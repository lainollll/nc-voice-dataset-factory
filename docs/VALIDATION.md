## Native GUI access violation during training

Windows Application events 1000/1001 identify the main app process with exception
0xc0000005 (-1073741819) in `shiboken6.abi3.dll`, offset 0x17471. The training venv
does not contain that module. The preserved run reached step 52 and contains a
step-50 checkpoint with adapter, optimizer, scheduler, RNG and trainer state; no
completed adapter is claimed for that interrupted run. The native dump's stack
scan contains Shiboken object destruction and Qt object cleanup addresses. This
is evidence about the failing subsystem, not a complete unwound backtrace or proof
of the exact Python-level trigger. No packages were reinstalled for this crash.

Inspection found `TaskRunner` released Python worker/thread references on
QThread.finished and independently scheduled thread deletion. Qt documents that
native/TLS cleanup can continue after that signal. The shared runner is now kept
busy and owns both wrappers until a zero-timeout thread wait succeeds, polling
through a 5 ms Qt timer. It then schedules thread deletion and emits the existing
completion signal. This is a localized shared-core change because diagnostics,
dataset tasks and training preparation all use this same runner. It preserves
result/error forwarding, reuse, safe close and UI responsiveness. The launcher now
enables Python's native-fault stack reporting with `-X faulthandler`.

The regression failed before the change because wrappers were released before
the simulated native-cleanup gate. It now checks that the gate is actually polled,
that UI heartbeats continue while it is held, and that completion emits once after
release. A first full run exposed an ordering flaw in that new test (144 passed,
one failed); review identified the missing wait-for-poll condition and it was
corrected. The strengthened targeted case passes. 500 rapid GUI worker cleanup/
restart cycles passed before and after the change: **the exact reported native
crash has not been reproduced, and this hardening is not proof of its resolution**.
Independent review found no actionable production-code issues.

The user's restarted training run was left untouched. Original datasets, caches,
model weights, interrupted logs and checkpoints were preserved.

Reference: [Qt QThread completion and wait semantics](https://doc.qt.io/qt-6/qthread.html#finished).
