## Confirmed load-bearing integration bugs

1. **`Pipeline.run` — `NEEDS_ATTENTION` dead-ends on zero remaining pending samples when `text_source` yields duplicates.**
   - Counterexample: `text_source` returns `list(TextItem)` that all collapse to keys already in `samples` (this is exactly what a duplicate-heavy LLM source produces; `add_texts` uses `INSERT OR IGNORE` on `UNIQUE(language, spoken_key)`). `repo.add_texts` returns 0, `next_pending` still `None`, falls to `update_job(..., "NEEDS_ATTENTION", error="needs_text")` and breaks. Run stops permanently while `attempts < attempt_budget` and `target` unmet.
   - Mitigation depends on `generate_llm_corpus` diversity (not shown). If its `DiversityIndex` only dedupes within a batch and not against `samples` rows, `text_source` will hit this every batch near the end of a large run. The 1000-run currently >300 accepted may be masking this by sheer luck of category/word variety.

2. **`Pipeline._attempt` mutable `fields` leaks stale keys into the failure path.**
   - Lines: `fields` is initialized `{}`, then partially populated before `write_wav_atomic`, `fingerprint`, `checker.check` etc. The `except` branch calls `finish_attempt(attempt_id, state="FAILED", error=error, reasons=[error], **fields)` with whatever was populated *before* the exception, not the final canonical set. Specifically, `original_path` is written to `fields["original_path"]` before `fields = dict(...)` reassignment, but the reassignment includes `original_path=str(original_path) if original_path else None` — so a pre-`write_wav` failure (e.g. `backend.synthesize` raising) has `{"original_path": <path>}` merged into a `state="FAILED"` attempt row. Counterexample: `keep_original=True`, `synthesize` raises → attempt row records `state=FAILED, original_path=".../original/xxx.wav"` for a WAV that was never written. `recover()`'s `known` set then treats that nonexistent path as belonging to an attempt, so the orphan detector won't flag it, and the file-format validator (`_relative_file` / `read_audio`) also won't run since `original_path` isn't validated by `finish_attempt`. Load-bearing because the failure-journal row now makes the recovery report a false positive on `original` dir.

3. **`ui/text_page.generate_preview` — `raise ValueError` inside worker still emits `result`, `_preview_ready` expects a 3-tuple.**
   - `Worker.run`: `except Exception: self.error.emit(traceback.format_exc())` — good, `_preview_ready` not called. But `_finished` runs `job_selector.setEnabled(True)` unconditionally: fine.
   - Actual integration issue: `import_preview` calls `self.task_cancel.clear()` only via `run_task`, but `generate_preview` captures `self._task_cancel` **inside** the closure (`self._task_cancel`) — so `stop_job`'s `self._task_cancel.set()` will cancel *the next* generation too if the user hits stop after this task returns but before `run_task` resets it in a subsequent call. `run_task` does `self._task_cancel.clear()` on entry, so sequence Stop→Generate is safe. Sequence Generate→Stop→Generate is safe. No confirmed bug here without `text.generate_llm_corpus`, so I flag it as **unconfirmed / needs the text.py source**.

4. **`Repository.review("regenerate")` — `generation_text = training_text` is *not* what the pipeline actually synthesizes for a fresh (non-reviewed) sample.**
   - `pipeline._attempt`: `spoken_text = sample.get("generation_text") or sample["spoken_text"]`. After `regenerate`, `generation_text` = `training_text`, so `spoken_text` for the new attempt is `training_text`, **not** `spoken_text`. The stated invariant ("immutable spoken_text/original preserved; per-attempt parameters actual spoken") is respected, but note this means a second `regenerate` is idempotent (still = `training_text`), never picks up a user-edited `spoken_text`. That matches "explicit regeneration uses samples.generation_text while immutable spoken_text/original preserved" **only if** the intent was regeneration-to-current-training-text; if the intent was regeneration-to-*original source phrase*, this is inverted. Flagging as a **semantic check needed**, not a bug, since the required invariant text is ambiguous.

5. **`export.export_dataset` — `attempt_id` recorded from `sample["latest_attempt_id"]` but text/audio come from the accepted attempt; mismatch possible after `review("accept")` on a sample whose latest attempt is `FAILED` (state was reset to PENDING by a later retry, `latest_attempt_id` overwritten).**
   - Counterexample: sample accepted manually via `review("accept")` → later, unrelated `retry` on the *same* sample moves it back to PENDING, `begin_attempt` sets `latest_attempt_id` to a fresh FAILED attempt, then `review("reject")` or user leaves it. But export only iterates `state="ACCEPTED"`, and `begin_attempt` requires `state='PENDING'`, so an accepted sample can only re-enter `begin_attempt` via a review action first. Contract holds. **Not a confirmed bug** — noted for completeness.

6. **`Repository.recover` orphan set derived from `attempts.path` and `attempts.original_path` only — misses samples whose audio was written but the attempt row was never created.**
   - Counterexample: hard process kill after `write_wav_atomic` in `_attempt` but before `finish_attempt`. `begin_attempt` already created the row, so `attempts` has a row with `path IS NULL`; the orphan scan marks the file as orphan (it lacks `attempts.path`). But `recover()` only reports `orphans`; it does not delete them. `report["orphans"]` grows unbounded on repeated crashes. **This is by design (report-only)** per `recover` docstring — not a bug, but the 1000-run durability claim should note that `recover()` does not reclaim these.

## Summary

- **Fix #1:** confirmed correct in provided code.
- **Fix #2:** confirmed correct in provided code.
- **Fix #3:** cannot confirm; `text.generate_llm_corpus` not supplied. The same-batch duplicate handling is fine at `add_texts`, but the downstream `Pipeline.run` behavior on 0 pending candidates (finding 1) is the actual correctness risk and *is* load-bearing.
- **Other candidate:** finding 2 (`_attempt` failure-path `fields` leak) is a real, reproducible integration bug in the provided code, independent of the three announced fixes, introduced by the new `fields` pre-population before `write_wav_atomic`.

Recommend before integration: (a) patch finding 2 by rebuilding `fields` (or setting `original_path=None` on failure) so FAILED attempts never carry a path for audio that was not atomically committed; (b) either confirm `generate_llm_corpus`'s `DiversityIndex` dedupes against the existing `samples` set (via a `text_source` callback that receives existing keys) or make `Pipeline.run` treat "candidate yields 0 new rows" as a distinct status (e.g. `NEEDS_TEXT_SOURCE_EXHAUSTED`) rather than re-entering the same loop; (c) add one test asserting `_attempt` failure retains no `path`/`original_path` in the FAILED attempt row.
