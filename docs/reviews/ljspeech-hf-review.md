## Load-bearing defects (concrete counterexamples)

**1. Filename collisions silently drop/replace rows (correctness + validator blind spot).**
`filename = source.name` and `expected = {Path(record["filename"]).name: record ...}` and `mapping[row["file"]]`. If two accepted records have identical basenames in different subdirs (e.g. `a/seg0001.wav` and `b/seg0001.wav`), then:
- `expected` collapses to 1 entry but `accepted` has 2 → writer emits 2 rows with the same `file`.
- Validator: `set(mapping) != set(expected)` passes (1==1 by dedupe? Actually `mapping` dict also collapses to 1). Then `info["accepted_count"] != len(expected)` → `2 != 1` → raises. So *export* succeeds and *validation* fails afterward, leaving a published-looking artifact. Worse: if writing precedes validation only in staging, you get a late hard failure instead of an early guard.
Fix: build `expected` from `accepted` (not a set/dict on basename), reject duplicate basenames up front with a clear error.

**2. Shard rotation drops a row's contribution when the first record exceeds budget but is exactly at boundary.**
Look at the boundary check: `if writer is not None and shard_bytes + len(wav) > max_shard_bytes`. With `max_shard_bytes=1` and each wav >1 byte, the *first* record sets `writer=None` path → new shard; second record triggers flush+close of a 1-row shard. That is fine. But the **last shard's `shard_bytes` is never checked after append, only before the next append** — that is correct behavior for one-record-dominant shard. No real bug here; the actual bug is `shard_bytes` is not reset when writer closes on rotation before the `if writer is None` block resets it. Trace: on rotation branch, `flush(); writer.close(); writer=None; shard_counts.append(shard_count)` — **`shard_count` is not reset here**, only inside `if writer is None:` which then runs next. That is fine because it's reset immediately after. OK.

Real shard bug: `shard_bytes` accumulates `len(wav)` even though Parquet compressed size ≠ `len(wav)`. Budget is advisory — not a correctness defect but the name `max_shard_bytes` is misleading; document it as raw-PCM budget.

**3. `duration` in mapping is computed from `len(converted)/SAMPLE_RATE`, but validator compares against `sf.info(wav).duration` and `original["duration"]` with tolerance `1/SAMPLE_RATE`.** `len(converted)` is in samples; `SAMPLE_RATE` int division yields float — fine. But `original["duration"]` is at **24000 Hz source**; resampling to 22050 changes frame count by rounding (`round(n*22050/24000)`). For a 3-sample source (`0.000125 s` at 24k → 3*22050/24000 = 2.756 → 3 samples at 22050 = 0.000136 s), difference = 1/22050 exactly, and float comparison `> 1/SAMPLE_RATE` fails at the boundary. Counterexample: very short clips near tolerance edge cause flaky validation. Fix: use `>=` with epsilon, or compare resampled frame counts precisely.

**4. `card.split("---", 2)` fragility.** If `spoken_text` in the embedded YAML list of languages ever contained `---` (it can't here since languages come from `record["language"]`), but more concretely: `README.md` body counts `---` occurrences; the metadata block itself contains no `---`, so `len == 3` holds. No bug, but note: `languages` could be empty set → `"\n".join([])` = `""` producing `language:\n` (null), and `yaml.safe_load` gives `language: None`; validator never checks `metadata["language"]`, so this slips through silently. Also `metadata["configs"]`/`dataset_info` access raises `KeyError` (not `ValueError`) if missing → validator surfaces `KeyError` not a clean issue. Wrap in a check that those keys exist and are the right type.

**5. `qy.Features(...)` schema equality with `check_metadata=True` on read.** `pq.ParquetFile(path).schema_arrow` for an `Audio` struct written from pylist may not carry the same HF `Features` metadata unless `Table.from_pylist(..., schema=schema)` preserves it — it does not propagate HF `Audio` feature metadata into Arrow field metadata automatically in all `datasets` versions. If it doesn't, the test `parquet.schema_arrow.equals(schema, check_metadata=True)` will fail on a *correct* export. Concrete risk: your validator may reject valid files on `datasets>=2.19`. Recommend `check_metadata=False` for the structural check and separately assert sampling_rate via the reader you already do at row level.

**6. `records` iterated twice for `accepted` and for `languages`/rows; after `flush()` at end you call `writer.close()` then set `writer=None` then `shard_counts.append(shard_count)` — if `accepted` is empty the earlier guard catches it, so `writer` is non-None at end. OK, but if the *first* record raises in `sf.write` before any `writer` is created, `finally` handles None. Fine.

**7. `_features()` imports inside function on every call** in writer and validator → on Windows with many shards, per-call import is cheap but calling `_features()` once per shard's schema is not (you call it once — good).
