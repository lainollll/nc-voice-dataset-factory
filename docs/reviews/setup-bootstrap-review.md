**Concrete issues (setup_windows.ps1 / setup.cmd)**

1. **`py` launcher argument bug.** `Read-Python311Path` is called with `-Command $launcher.Source -Prefix @('-3.11')`. If `py.cmd`/`py.exe` emits any stdout (the real launcher does not, but a shim could), fine — but more importantly on success `$response` may contain multiple lines; `Select-Object -Last 1 | ConvertFrom-Json` is correct. However `& $Command @Prefix ...` with `$Command` from `Get-Command py` uses `$launcher.Source` (the .exe path). That's fine. **Real bug:** if `$launcher.Source` is a `.cmd/.bat`, `&` works, but `2>$null` on native stderr combined with `$ErrorActionPreference='Stop'` under PS 5.1 is OK. Not a defect — flagging only that `py -3.11` returning the *base* interpreter when a 3.11 is registered is expected.

2. **`Test-SetupTool` swallows exit-code semantics for `ffmpeg`.** `ffmpeg -version` exits 0, ok. But after WinGet installs FFmpeg, the shim `ffmpeg.exe` lands under a WinGet links dir that may not be on the *current* process PATH until `Refresh-SetupPath` runs — it does run inside `Install-SetupPrerequisite`, so the re-test should see it. **However** WinGet installs to `%LOCALAPPDATA%\Microsoft\WinGet\Links` which is added to the *User* PATH by WinGet only sometimes; `Refresh-SetupPath` re-reads User/Machine PATH, so this depends on WinGet updating them. If WinGet does not (e.g., `--scope machine` vs user mismatch), the post-install re-test throws even though the tool is installed. Concrete: after `Install-SetupPrerequisite`, also probe the well-known WinGet Links dir explicitly and prepend it to `$env:Path`.

3. **PATH dedupe trims trailing `\` for the key but emits the untrimmed `$expanded`.** `$seen.Add($expanded.TrimEnd('\'))` while `$expanded` may still end in `\`, so `C:\Foo\` and `C:\Foo` collapse (good) but two entries `C:\Foo\` then `C:\Foo` produce the first verbatim. Harmless but inconsistent; not a safety bug.

4. **`Find-Python311` fallback candidates don't cover the WinGet-installed location.** After `winget install Python.Python.3.11`, the interpreter is typically in `%LOCALAPPDATA%\Programs\Python\Python311\` (covered) — OK. But `py.exe` may be a *new* launcher in `%LOCALAPPDATA%\Microsoft\WindowsApps` that isn't on the pre-refresh process PATH; `Refresh-SetupPath` runs, so `Get-Command py` should find it. Acceptable.

5. **`setup.cmd` `pushd "%~dp0"` then `setlocal`.** `setlocal` precedes `pushd`, and `popd` + `exit /b %SETUP_EXIT_CODE%` runs after `endlocal` is implicit — fine. **Concrete:** if `pushd` succeeds but PowerShell raises and `popd` never runs on the `throw` path, the drive is left pushed in the caller's cmd window. The errors are caught by `%ERRORLEVEL%` so `popd` runs — OK.

6. **`setup.ps1` truncation.** `$requirementsName` + core install shown; the `Models` branch shown; `Exports`/`Speaker`/`Development` handling and trailing `chatterbox` failure check are **not in the provided source**. Cannot confirm `-Exports`/`-Speaker` install anything, nor that pip failures exit non-zero after the last command. This is the highest-risk gap: if `chatterbox` install fails, `$LASTEXITCODE` is not re-checked before the script ends, PowerShell exits 0, and `setup_windows.ps1` reports success. Add an explicit `if ($LASTEXITCODE -ne 0) { throw ... }` after every pip call.

7. **Test `test_setup_bootstraps...` asserts exact order `Python, Git, FFmpeg`.** Correct given the loop, but `ffmpeg` name shadows real ffmpeg only while `tools` is prepended — fine. **Concrete:** the fake `python.cmd` exits 1 and is never exercised because `py` succeeds; if `py` were absent the fake `python` is skipped only by the `WindowsApps` check — the fake isn't under `WindowsApps`, so it would run and fail, then fall through to LOCALAPPDATA candidates. Test doesn't cover that path.

**Highest priority:** (2) WinGet-Links PATH gap and (6) missing per-pip exit checks in the unseen remainder.
